# Revision source artifacts — provisional P0-R2 operations

This is an internal implementation candidate, not ED-26 approval or production certification. Do not infer external inference approval from credentials or from these instructions.

Run Node, Python HTTP and ingestion workers with the same original-document storage and revision index storage. Set `INGEST_UPLOADS_DIR` to each service's mount of the uploads volume, and `FAISS_INDEX_DIR` to each service's mount of the FAISS volume. Configure matching service authentication with `AI_SERVICE_API_KEY`. Python HTTP liveness `/health` does not certify a worker, source or index.

The current `docker-compose.yml` runs Python HTTP and an ingestion worker, not Node. Both Python services mount `ednova_revision_faiss` writable at `/app/faiss`: ingestion creates an index and the authenticated source-preparation HTTP endpoint creates the reviewed revision's exact artifact. `docker-compose.ai.yml` shares the same named index volume and the external `ednova-api_study_uploads` volume. Host-run Node does not automatically see Docker named volumes; configure compatible shared mounts explicitly. When Node is containerized, mount its index view read-only. Index files are committed readable by the Node user; originals are captured read-only. The service filesystem and database are trusted operator boundaries, not hostile multi-tenant writable directories. Back up both volumes and Mongo together. Compose configuration validation does not certify an image, worker recovery or deployment.

An authenticated course author uses:

1. Upload/reupload an original through the existing course upload route. Node hashes actual bytes and creates `originals/<sha256>` without replacing existing content. Upload filenames and mutable course inventories are not publication identities.
2. Ingestion consumes the explicit draft revision. It extracts the verified originals, preserves document/chunk/hash/location identity and writes a revision artifact. LLM-enriched text is not relabeled original extraction. Text documents have unknown page location; PDFs carry actual extracted page numbers. Scanned/unsupported documents require a truthful extraction procedure before publication.
3. Edit/review the draft. An edit changes its revision tag with a conditional version update and invalidates old readiness. It does not modify an old published revision.
4. Call `POST /api/v1/study/courses/:courseId/draft/sources/prepare` with `{ "expectedRevisionTag": "the-exact-current-tag" }`. This explicit authoring operation verifies/captures originals, requests Python indexing and checks the local exact artifact. It is not automatic legacy migration during a read. A missing embedder/model, source or artifact returns unavailable. No heavyweight model download was performed for P0-R2 verification; local integration uses an explicitly test-owned deterministic embedder.
5. Generate a provisional Studio candidate, explicitly review/register it, then publish the same exact reviewed tag. Supported offline candidates complete a quotation from actual extracted text. They do not claim to assess arbitrary conceptual objectives. Unsupported source content requires instructor authoring. Answer keys are in the instructor-only evaluation proposal and server storage; learner activity projection excludes them.

Digital PDF text and page numbers are extracted in a fresh bounded Python subprocess (CPU, address space, page count, extracted text size and wall-clock limits). Revision indexing consumes those sandboxed pages instead of reparsing the original in the AI server. Unsupported or scanned originals without extractable text still fail closed; this does not certify OCR quality.

Storage layout:

- Uploads volume: `originals/<64-lowercase-hex-source-digest>`.
- Index volume: `<courseId>/<revisionId>.faiss` and `<courseId>/<revisionId>.meta.json`.
- Contract index reference: `faiss/<courseId>/<revisionId>.faiss`.

The internal sidecar includes schema version, course/revision/content pin, documents, source-manifest digest, index checksum, extracted chunks and complete chunk metadata. Each chunk records actual document, source hash, text hash, chunk ID, section and nullable page. Mongo pins the exact sidecar checksum (`artifactHash`) and index checksum. Node verifies bytes, document inventory and checksums before activation and protected reads. Python verifies the exact requested artifact before retrieval. A legacy course-only index cannot satisfy this boundary.

Filesystem writes use same-directory staging, flush/fsync, insert-only links and a sidecar commit marker. Interrupted or mismatched pairs remain unavailable. A conflicting rebuild needs a new revision, not overwriting a published pair. Original blobs and old published index files are not deleted during draft/source editing. There is deliberately no automatic garbage collector: an authorized retention/backup inventory must prove that no revision or recovery receipt references an artifact before a separate cleanup operation is designed.

Publication uses a persisted prepared revision followed by a compare-and-set active pointer and completion. An interruption can temporarily make latest resolution unavailable; retry the same exact publication command. It must not resolve an unrelated latest revision. Explicit old published/deprecated pins continue to resolve if their originals/artifacts and current grant remain valid. Revoked pins do not resolve. An activation that loses to another revision returns a conflict; its prepared record is retained for operator review rather than rewritten. Standalone Mongo offers no multi-document atomicity claim here.

Legacy migration/reindex is explicit and non-destructive. Inventory each exact original hash, prove bytes still exist, reconstruct/review source mapping and reindex under a new reviewed draft tag. If original bytes or revision provenance are missing, retain the legacy record and fail closed. Do not copy a course-only index into a revision directory and claim provenance. No deployment migration was executed in this mission.

Provider execution requires a separately approved task/model/request budget. The provisional `LLM_APPROVALS_JSON` operator allow-list uses per-agent records with `approvalId`, exact configured `model`, `task` matching the agent, Unix-seconds `expiresAt` and positive integer `maxRequests`. Configure the same explicit `LLM_BUDGET_MONGODB_URI` and `LLM_BUDGET_DB_NAME` for every Python HTTP and worker process before authorizing calls. Each dispatch first atomically reserves a request in `llm_approval_budgets` using majority, journaled writes; an approval ID is bound to its original task, model, request limit and expiry. Missing/expired approval, a ledger record with `revokedAt`, conflicting reuse, exhausted budget, unavailable database or an uncertain write fails closed. All processes must use the same protected ledger; a trusted operator must mark the ledger record revoked through an authorized operation. Before dispatch and before delivering a provider result, each process rechecks the ledger with majority read concern. A reservation is consumed even when a process or provider fails. Router retries and fallback chains are disabled for this path. Never put synthetic approvals in deployment configuration.

This provides a shared **request count** and operator-controlled ledger revocation, not a monetary/token budget or protection against a database operator altering the ledger. There is no administrative revocation interface yet. A request already dispatched cannot be cancelled retroactively; a revoke immediately after the pre-dispatch read can still race with dispatch, and delivery checks do not prove global cancellation. All instances must use the same protected durable database; an operator must manage authorization changes consistently and use a fresh approval ID for changed limits. Successful response metadata requires a nonempty result and matching model identity; unit simulations are not real inference. No approved external call has been performed. Production external inference still requires genuine owner/operator approval, a cost bound, token/cost enforcement, deployment security and recovery verification.

The canonical public contract candidate remains version 1.0.0 and NOT FROZEN. Internal source preparation, strict tutor transport fields (chunk/text identity and artifact checksum), internal `revokedAt` metadata (preserving `draft | published | deprecated` status vocabulary) and provider approval status are provisional semantics requiring owner review. Browser tutor projection omits service-only context, raw retrieval objects and storage references. These extensions do not create source grants or mastery. The optional ingestion `files[].fileHash` transport field is mirrored by Node/Python validators and is checked as SHA-256; captured original bytes remain authoritative.
