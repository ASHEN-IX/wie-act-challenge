# ED-26 v1.0.0 contract review candidate

**Implementation and fixtures are executable; human review and official freeze are pending.** M03-H applies the seven provisional engineering recommendations as a reviewable candidate patch; this is not owner approval. This is the proposed executable supplement for Contracts 03–07, 10/13, 15/16 and the minimal Contract 18 boundary. It creates no published-context endpoint, enrollment, renderer, attempt/evidence persistence, reward engine or facilitator behavior. Current personal ownership and all M02 access checks remain authoritative.

Canonical TypeScript definitions and inferred types live in `apps/api/shared/ednova/contracts.ts`; Pydantic mirrors live in `apps/ai/contracts/ednova.py`. This follows the existing AI-envelope/Bloom mirror-and-golden-fixture pattern. Both consume [the same synthetic fixtures](ednova-v1-fixtures.json). [JSON Schema](ednova-v1.schema.json) is a structural review/export artifact derived from those Pydantic models, not a third handwritten validator. `python -m contracts.export_ednova_schema --check` detects artifact drift; validators additionally enforce relationships that JSON Schema cannot express. No new validation dependency, generation framework, registry service or protocol is introduced.

## Version and serialization policy

All new root DTOs require exact `schemaVersion: "1.0.0"`. Activity components and evidence also require their exact supported versions. Unknown/missing versions, unknown types, properties and unsupported renderer versions fail closed with `INVALID_CONTRACT`; no field stripping or silent downgrade occurs. There is no negotiation endpoint. JSON is the wire representation; no dates, functions, class instances, NaN, Infinity, undefined or executable values belong in it. The TypeScript parser returns an explicit new validated shape and emits a generic error without rejected payloads. Python uses strict Pydantic models with `extra="forbid"` and the same generic boundary error.

Each DTO is capped at 65,536 UTF-8 bytes of compact JSON. Text limits count Unicode scalar values; unpaired surrogates are rejected. Integers must be nonnegative safe integers unless a stricter bound applies; booleans and numeric strings cannot coerce to numbers. JSON `20` and `20.0` have the same integer semantics. UUIDs are canonical lowercase v4; course IDs use the current lowercase 24-hex shape; other established/prefixed IDs use 1–128 alphanumeric/underscore/hyphen characters. Hashes are `sha256:` plus 64 lowercase hex digits. UTC timestamps use exact millisecond ISO format with ASCII digits only. Text fields are plain text; no HTML/Markdown/code execution is authorized by a string. Later shipped renderers must escape it.

An additive field is **not** compatible with a strict existing reader merely because it is optional in a new definition. Until frozen, coordinated candidate edits require both validators, schema export and fixtures in the same change. After freeze, any accepted-shape/meaning change needs an explicitly reviewed version and consumer support; incompatible major versions are rejected. Deprecated fields are not silently accepted. Migration of existing persisted records requires the owning later mission; nothing here rewrites historical room receipts/messages.

Existing broker `version: "1"`, HTTP adapters, unversioned room snapshots, room command receipts, peer-text DTOs and presence messages retain their exact wire versions and behavior. No new worker job/routing key is registered. Versioned activities cannot be smuggled into legacy room snapshots; existing reducers ignore the future `ROOM_ACTIVITY_STATE` type until a reviewed integration exists.

## Source identity and revision semantics

A source pin is `(courseId, revisionId, contentHash)`; an activity also pins `(activityId, activityRevision, activityType)`. The wire `revisionId` is the immutable `course_revisions.revisionTag`, scoped by `courseId`; the internal MongoDB `_id` is not a public or service-facing revision identity. Every owning service resolves `(courseId, revisionTag)` and must not substitute a newer revision, expose the persistence `_id`, or accept an inconsistent source/revision pair. Every linked reference must match the expected pin. `validateActivityContext` checks the full pin, allowed document membership/document hash and objective membership in the supplied published context. `validateSubmission` checks the full activity/source pin and allowed option or guided-step identities. `validateProposal` checks room ID, expected sequence and source pin against the supplied current context, including the source-free case. These helpers validate **relationships**, not current authorization or database existence; Nest must freshly resolve the context using the current actor/grant before calling them.

`PublishedContext` exposes title, published timestamp, authorized document IDs, provenance references and bounded topic/objective text. It excludes storage keys, vector indexes, editor identities, unpublished drafts and grading data. `SourceResolution` alone holds the server-only index reference, which is the exact relative artifact `faiss/<courseId>/<revisionId>.faiss`; directory-only, course-only, absolute, traversal, foreign-course, foreign-revision and non-`.faiss` references fail closed. The metadata sidecar remains a future runtime artifact at `faiss/<courseId>/<revisionId>.meta.json`; it is not an alternate `vectorIndexRef` value. `SourceResolution` requires a matching `allowed` decision. `GroundingContext` includes only authorized excerpts and source references; excerpt document IDs must belong to its supplied sources. No embedding vectors or credentials are transmitted. A valid reference is not evidence that the current FAISS adapter is revision-aware; that adapter migration remains future work.

The persisted target revision vocabulary remains `draft | published | deprecated` from the data model. `reviewStatus: unreviewed | reviewed` is orthogonal candidate metadata: a reviewed draft is a publication candidate, not a new persisted revision status. Published/deprecated projections require reviewed status. `deprecated` expresses superseded immutable history, not implicit revocation: existing sessions may remain pinned if current access still permits. Published revisions cannot be edited in place. `UNPUBLISHED`, `UNAUTHORIZED`, `UNAVAILABLE`, `REVOKED`, `STALE_REVISION` and `UNSUPPORTED_VERSION` are access/resolution failures, not fabricated revision records. A stale result must not substitute the latest revision silently. There is no operational revocation/publication service here.

Access-decision `userId`, grant and checkedAt are server-derived. The schema can represent future `active_enrollment` and `assigned_instructor` decisions, but M02's personal-owner predicate remains the sole implemented source grant. A browser-provided decision/revision or invitation is never authority. Later ED-04/ED-05 services must create/revalidate real grants and immutable publications.

Provenance supports extracted/manual/AI-generated labels, document content hash, and page number or explicit unknown location. `locationKnown` must agree with nullable pageNumber. Unknown page locations are not fabricated. Excerpts are service-only; source references carry no private filesystem path.

## Trusted activities and limits

Only exact `InteractiveQuiz` and `GuidedProblem` are P0. `componentVersion: "1.0.0"` identifies the proposed trusted renderer contract, not an installed component. ED-27 will implement those allowlisted components. Unknown variants fail, with no executable fallback. Public definitions have sourceRefs, objective, title, instructions, language, source/activity revision, optional-by-null time limit and public constraints. Renderer settings do not contain hidden grading thresholds.

Bounds: title 200 scalars; instructions/question/step prompt 4,000; quiz option labels 1,000 with 2–20 unique options; guided problem text 8,000 and 1–20 unique steps; source references 1–32; maxAttempts 1–20; time limits 1–86,400 seconds or null. Public properties are fully enumerated. Answer keys, solutions, rubrics, evaluator prompts, executable markup fields, credentials and private evidence are rejected even when nested inside presentationData. A schema cannot detect a secret intentionally encoded as ordinary instruction text; the owning projection/review boundary still must prevent that disclosure.

`ServerEvaluationDefinition` binds a separate evaluationRef and rubricVersion to the exact activity/source revision. It holds bounded answerKey/rubric text and evaluator type. It is not nested into the public activity and cannot parse as one. Later instructor preview needs a separate authorized server projection, never hidden public JSON.

## Private attempts, results, evidence and rewards

Client submission contains only schema version, attemptId, full activity reference, nullable room ID, time spent and bounded answers. Quiz answers are unique selectedOptionIds; single-select permits exactly one. Guided answers contain unique known step IDs and bounded plain text. Client actor, score, acceptedEvidence or authoritative lifecycle fields are invalid. `readAttemptSubmission` derives the actor from the existing domain request; owning source ACL checks remain required. The stored `PrivateAttempt` adds userId, payloadHash, submittedAt and the existing target lifecycle `in_progress | submitted | graded`.

Attempt receipt identity is `(authenticated userId, attemptId)`, independent from room `(roomId, actorId, commandId)` receipts and peer submission IDs. A first valid submission must persist the normalized full payload/activity pin and its hash before evaluation. Identical retries/concurrent identical submissions must share one receipt/result. Same identity with changed content/operation is conflict (409); no grade recomputation. Lost acknowledgment/restart requires retrying the same identity/payload against durable authoritative storage. Changed activity revision, revoked access and unsupported schema fail before accepting a new receipt; current actor/source checks apply to recovery too. ED-29 must implement atomic persistence, races and restart behavior; M03's `compareAttempt` only classifies validated payloads as identical/conflict/new. It is not a durability guarantee or database claim.

The prose Contract 05 UUID requirement/data model takes precedence over its illustrative `att_...` sample; the candidate uses lowercase UUID v4. The durable receipt identity is `(authenticatedUserId, attemptId)`: an `attemptId`-only lookup is non-unique, and the target unique indexes are `{ userId: 1, attemptId: 1 }` for attempts and evidence. Result `graded` retains Contract 06 vocabulary and now includes required-but-nullable `socraticHint` and `recommendedNextStep`. A hint is at most 8,000 plain-text scalars; a next step, when non-null, contains only `type: "advance"`, `nextObjectiveId` and a 200-scalar title. These fields are recipient-only and must not appear in `PublicCompletion` or room projections. Transport/recovery states are pending/rejected/failed/unavailable, with matching bounded codes and retryable flags; these are not new persisted attempt states. Graded private feedback is bounded at 8,000 scalars and score at [0,1]. Evaluator completion does not accept evidence: evidenceId may still be null. `parseRecipient` checks a private DTO against its authenticated recipient; knowing an attempt ID, being presenter, instructor or admin grants no result access. Current runtime authorization remains mandatory.

Only the Learning service may create an `accepted` evidence record after validating actor, source/activity revision, assessment, evaluator provenance and policy. `EvidenceDecision` separately represents rejected/unavailable with no fabricated evidence record. `AcceptedEvidence` is server-only, keyed by evidenceId with a unique actor/attempt relationship; it retains version, objective, score, Bloom and explicit masteryAchieved (never inferred merely from submission). Model-based evidence requires a model alias and REAL_APPROVED provenance; schema parsing does not establish that a real call/validation happened. Deterministic synthetic fixture evidence is MOCK_TEST and must never be awarded in a real environment. UNAVAILABLE/uncertain model responses are not accepted evidence.

A room-approved `PublicCompletion` has a stable completionId, room/activity pin and aggregate count 0–10. It has no user ID or evidence ID. Learning acceptance and permission to disclose completion are separate decisions. `RewardReference` is server-only and connects evidenceId, optional completionId, rewardCandidateId, policyVersion, optional finalAwardId and the existing `xp:{userId}:{evidenceId}` event key. Evidence owns learning acceptance; the existing reward owner alone later writes a final award (ED-33). No XP amount or numerical reward is model/client-authoritative.

## Rooms, proposals and private help

Future `ROOM_ACTIVITY_STATE` binds the source/activity pin to roomId/seq/currentPhase/presenter and a public roster of at most ten unique members. The pin and activity are both nullable for source-free rooms: `activity != null` requires a matching non-null pin, while `pin: null` requires `activity: null`. A course-backed room without an active activity retains a valid pin and null activity. Presenter must be a member; count cannot exceed roster size. It does not redefine the existing ROOM_STATE_SYNC event or persist presence. `SelectActivityCommand` carries commandId, expectedSeq and DISPLAY_ACTIVITY; later owning services must check current membership, presenter, source access, activity relationship and existing durable command rules. This mission does not activate that command.

Room durable `seq`, per-room peer message `seq`, and ephemeral presenceEpoch/presenceVersion remain separate order domains. No attempt/evidence identity is a room command receipt. Reconnect continues using the existing authorized snapshot/history; candidate contracts add no polling, gateway or transport.

`FacilitatorContext` uses bounded public dialogue and public counts only. It excludes private attempts, feedback, help, evidence and evaluator definitions. Its source pin is nullable with the same invariant as room state: a source-free context has `pin: null` and `activity: null`; a non-null activity requires a matching pin. A proposal uses existing Python `messageText` (not the old illustrative spokenResponseText), an allowlisted strategy, an optional source pin and optional DISPLAY_ACTIVITY proposal. A source-free proposal has `pin: null` and no UI command; a source-backed proposal keeps a matching pin. Only Nest may validate it, and only a subsequent presenter-authorized durable mutation can produce accepted status. A stale/malformed/unavailable proposal never directly mutates a room. Proposal decisions use a closed mapping: `rejected` allows only `UNAUTHORIZED`, `UNPUBLISHED`, `REVOKED`, `UNSUPPORTED_VERSION`; `stale` allows only `STALE_REVISION`; `unavailable` allows only `UNAVAILABLE`. Legacy trigger/reasoning/target fields are not silently forwarded into this new public-compatible candidate; legacy ED-09 behavior remains unchanged. Richer actions need separate reviewed versioned definitions, not arbitrary strings/code.

Private-help client requests contain no actor; recipient-only responses bind userId and requestId. Unavailable responses carry no tutor text. Private help/results cannot parse as room activity state or public completion. No private-help feature is implemented.
